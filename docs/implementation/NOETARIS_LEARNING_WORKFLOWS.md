# Governed reflection workflows: pagination and policy foundation

The next UI integration needs complete proposal navigation and source-bound creation before it can safely expose review controls. This document records the backend foundation. The proposal creation/review UI is now integrated; see NOETARIS_REFLECTION_UI.md and current-evidence.json. Broader claim/promotion/retention work remains open.

GET /v1/learning retains reviewer/admin permission and the prior default maximum of100 records, and now supports explicit limit1-100, actor/view/state-bound keyset cursor and state filter all/candidate/reviewed/rejected. Responses retain items and add total, has_more, next_cursor, scope, filter, snapshot=false and authority_granted=false. GET /v1/learning/own requires propose permission and always restricts author to the current verified operator, including shared legacy project roles. It defaults to25 records. A cursor carries a position, never authority; different identities, view modes and filters reject it.

Each row includes its original proposal and an attributable source_claim projection (source document, locator, original hash, claim status/revision and subject/predicate/value). All joins use current database RLS. Review listing does not expand private-source access. Own views do not expose other authors. Revoked source access withholds records; restoring access recovers the same retained proposal and text. The listing does not promote any reflection into canonical knowledge.

A real private-source regression exposed an existing insert-policy ambiguity: inside learning_create, unqualified source_ids/provenance_complete referred to the candidate claim, whose reviewed-derived fields legitimately remain empty/false. Authorized private candidate reflections were consequently blocked. Migration0037_learning_proposal_provenance.sql explicitly binds checks to learning_proposals while preserving source-claim visibility, exact author, inclusion of the originating document and complete current authorization of the proposed source set. It rewrites no records, grants or independent-review rules. Unknown/missing provenance and forged authors remain rejected. The generated access-definition contract was rebuilt against an owned clean PostgreSQL instance.

Focused tests exercise165 retained records beyond the former100-row bound, full keyset traversal without duplicates, actor/filter/view cursor isolation, invalid bounds, real role HTTP checks and the unchanged individual503 gate. Private storage tests create an actual proposal against a shared candidate source, reject empty/incomplete/forged source provenance, withhold after revocation and recover exact original text after regrant. These are source-mounted/packaged application and real PostgreSQL policy proofs, not individual HTTP admission or independent semantic acceptance.

The owned0036-to-0037 rehearsal uses the exact previous API package to write a source, proposal and full26k assistant receipt. It backs up the quiescent synthetic database, applies the new migration, compares all50 table row fingerprints except the intentionally additive journal entry, checks unchanged sequences and all access definitions except learning_create, reapplies idempotently, then restores the pre-upgrade backup into a separate database and reapplies standard role provisioning before checking exact data/access/sequence recovery. Role/database-level provisioning is required in addition to pg_dump. No live resources, real user data or credentials are selected.

Deployment/rollback: the new API requires the exact0037 migration and packaged access contract. Rehearse and back up an owned candidate before any later approved rollout; this work has not migrated the existing live database. The previous API requires its prior schema journal. To roll back a quiescent candidate, restore the admitted pre-upgrade backup into a separate database, provision the standard app role, verify full fingerprints/ACLs/sequences, then pair the previous exact image. Do not overwrite a database containing subsequent user writes with an older backup: preserve current state and reconcile every later write before switching, or use a forward repair. This rehearsal does not certify rollback after concurrent post-cutover activity.
